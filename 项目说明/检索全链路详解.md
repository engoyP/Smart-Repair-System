## 1. 全景总览

### 1.1 一条链路图

```
用户消息 "注塑机温度过高"
        │
        ▼
[0] 错误码预检 extract_error_codes（纯正则，零 LLM）
        │  含错误码（SV0436/6401）→ 手册双路参与，最多 4 路
        │  无错误码 → 只走知识库 2 路
        ▼
[1] 查询关键词提取 QueryExtractor  —— 白名单优先 + LLM 兜底
        │  "注塑机 温度 过高"
        ▼
[2] 双路/四路并行召回 ───────────────┬─────────────────────────┐
        ▼                           ▼                         ▼
[2.1] 知识向量路               [2.2] 知识 BM25 路      [2.3] 手册双路（仅含错误码）
  Milvus IVF_FLAT+COSINE    PG ILIKE 加权评分        精确匹配(score=1.0) + 语义向量
  top_k（语义）              top_k（关键词）           top_k=5 / top_k=5
        │                       │                         │
        └───────────┬───────────┴────────────┬────────────┘
                    ▼
[3] RRF 融合  Σ 1/(60+rank)   —— 只看名次，跨源分数不可比
        │  去重键：_dedup_key > knowledge_id > id
        ▼
[4] 候选过滤  剔除 rrf_only 且 score<0.15
        ▼
[5] 加权重排  设备不匹配×0.2 / 命中率<0.3→×0.15 / ≥0.3→×(1+0.4×ratio)
        ▼
[5.5] 严格过滤（问答/专家模式额外）  设备精确匹配 + 故障关键词命中，空则回退宽松 top2
        ▼
[6] TopN 注入 Prompt → LLM 生成回答（只引用案例内容，不编造）
```

### 1.2 三阶段设计哲学

| 阶段 | 负责 | 解决什么问题 |
|---|---|---|
| 召回（2） | 把可能相关的都捞进来 | 漏检 |
| 融合（3-4） | 统一多路分数、清掉噪音 | 分数不可比、假命中 |
| 精排（5-6） | 按真实相关度定胜负 | 排名太粗糙 |

### 1.3 检索入口矩阵（四种入口，一套链路）

> **关键点**：四者共用**同一个知识库**（PG `knowledge_items` + Milvus `knowledge` 集合 + 手册库），
> 共用**同一套检索编排层**（`retrieval_flow.py`：`retrieve_hybrid` + `filter_rerank_cases`），
> 差异只在"检索流程复杂度"与"Agent 分工"。

| 入口 | 定位 | 检索方式 | 重排后取几条 |
|---|---|---|---|
| AI 知识问答（Search.vue，`/search/agent`） | 一次性捞历史案例、**可追溯** | ReAct 循环（LLM 选策略，≤5 轮） | top_k（前端默认 8） |
| 智能问答（AiAssistant，`/answer/stream`） | 直接给结论式回答 | 固定混合检索（`retrieve_hybrid`）+ 严格过滤 | 最多 8 条 |
| 追踪维修（`/guided-repair`） | 一步步引导排查 | 轻量双路 + GuidedRepairAgent | Top3 |
| 钉钉机器人（robot_graph / MCP） | 移动端快捷入口 | robot_graph 按意图分发；`search_knowledge` | Top5 |

### 1.4 检索链路上的索引支撑（对称性）

两条检索路都有索引支撑，**数据增长不拖累任何一路**：

| 路 | 存储 | 索引 | 详见 |
|---|---|---|---|
| 向量路 | Milvus（`knowledge` / `log_code` 集合） | **IVF_FLAT + COSINE**（nlist=1024，检索 nprobe=16） | 第 8.1 节 |
| BM25 路 | PostgreSQL（`knowledge_items`） | **pg_trgm GIN**（`title`/`content` gin_trgm_ops，migration `7a8b9c0d1e2f`） | 第 8.2 节 |

## 2. 查询理解：关键词提取（QueryExtractor）

> 代码：`backend/app/agents/query_extractor.py`

### 2.1 怎么计算

1. **构建白名单**（缓存 5 分钟，`_whitelist_ttl=300`）：
   - 内置设备词（`_BUILTIN_DEVICE_TERMS`，约 20 词：注塑机/数控机床/CNC/液压系统/传送带/空压机/变压器/电机/锅炉/制冷系统/机器人/PLC/机床/加工中心…）
   - 内置故障信号词（`_BUILTIN_FAULT_SIGNALS`，约 60 词：故障/报警/过热/异响/跳闸/不转/泄漏…）
   - 从 DB 动态加载所有已发布知识的 `device_type` 与 `fault_tags`（`query_extractor.py:83-101`），实测一度共 **151 词**
2. **按词长降序匹配**（长词优先，避免"PLC"吃掉"PLC系统"，`query_extractor.py:120-128`）
3. **补提英文/数字 token**（`PLC`、`RAM`、故障码 `6101`，`query_extractor.py:130-140`）
4. **命中 ≥1 个** → 空格拼接返回；**0 命中** → 调 DeepSeek 提取关键词（结果缓存 10 分钟，`_llm_cache_ttl=600`；LLM 超时 15s、失败降级返回原始查询，`query_extractor.py:144-187`）

### 2.2 为什么这样计算

- 白名单来自**知识库本身的真实标签**（device_type / fault_tags），词表与业务数据同源，命中率天然高
- 中文没有空格，关键词提取是后续一切匹配的基础（向量编码、ILIKE 切词都吃它）
- **0 命中才动用 LLM**，控制成本与延迟；LLM 兜底也带缓存，相同提问不重复调用

### 2.3 好处

- 先过滤掉口语干扰词（"请帮我看看…"），让 embedding 和 ILIKE 都针对纯技术词，**避免语义向量被噪声带偏**（tools.py:604 / 648 均标为"关键优化"）
- 实测：`注塑机温度过高 → 注塑机 温度 过高`

> **本环节在检索链路中的位置**：它同时服务三处——向量路编码前清洗、BM25 路切词前清洗、加权重排的 fault_kw/device_kw 来源（详见第 5.2 节）。一套提取器贯穿"召回+精排"，保证词表口径一致。

## 3. 召回阶段：双库多路检索

> 公共编排层：`backend/app/agents/retrieval_flow.py` 的 `retrieve_hybrid()`（L42）——
> **检索逻辑唯一实现**，智能问答 / 专家 / 钉钉 / 搜索页共用，避免"检索逻辑写多遍导致策略漂移"。
> 历史遗留端点（/quick、/hybrid、/manual-lookup）同样复用它。

### 3.1 统一入口 `retrieve_hybrid`

```python
def retrieve_hybrid(query, top_k=10, device_type=None, fault_code=None):
    tools = make_tools()                 # 构造检索工具集（单一入口）
    error_codes = extract_error_codes(query)   # 错误码预检（第 3.2 节）
    result_sets = []
    # 知识库双路（总是走）
    vector_result = tools.vector_search(query, top_k, device_type, fault_code, score_threshold=0.0)
    bm25_result   = tools.bm25_search(query, top_k, device_type, fault_code)
    # 手册双路（仅当提取到错误码）
    if error_codes:
        manual_exact = tools.manual_code_search(error_codes, device_type, top_k=5)  # 精确，score=1.0
        manual_vec   = tools.manual_vector_search(query, top_k=5, device_type)       # 语义
    merged = rrf_merge(result_sets, top_n=top_k)
```

### 3.2 错误码预检：决定 2 路还是 4 路

`extract_error_codes`（tools.py:441，纯正则零 LLM）提取错误码/报警码：

- **字母+数字混合 token**（`SV0436` / `ALM-6401` / `E3091`）→ 去分隔符 + 大写归一化（`ALM-6401`→`ALM6401`），长度 ≥3 且非纯数字
- **纯数字 4~6 位**（`6401` / `0401`）→ 视为报警码，但**排除年份**（恰好 4 位且 `19`/`20` 开头不算）

**设计取舍**：
- **误判无害**（最多多查一路手册，结果里没有手册条目不影响回答）
- **漏判是已知边界**（非规范格式错误码提取不到 → 走 2 路，不启用手册权威答案）
- 用正则而非 LLM：零成本、可预测、无幻觉；语义理解交给后面的向量路和验证 Agent（职责分层）

### 3.3 知识库向量路（Milvus 语义路）

**流程**（tools.py:585 `vector_search`）：

```
query → QueryExtractor 提取技术关键词 → 编码（Qwen3-Embedding-0.6B）
      → Milvus knowledge 集合搜索（IVF_FLAT + COSINE，nprobe=16）
      → score_threshold=0.0 全量召回（不过滤，交给下游）
      → 可叠加 device_type / fault_code 标量过滤表达式
```

**编码细节**（embeddings.py）：
- Qwen3-Embedding-0.6B 本地加载（CUDA），1024 维
- tokenize 后取**最后一层 EOS token 的 hidden state** 作为整句向量
- **L2 归一化** → 向量长度压成 1，余弦相似度 = 点积：`cos(θ) = query · 知识`

**为什么**：余弦衡量"语义方向一致性"，对同义词/近义表达鲁棒（"温度过高"和"温度偏高"向量接近）；归一化让 COSINE 直接走点积，Milvus 索引友好。实测：`注塑机温度过高` 与《注塑机模具温度失控》余弦 **0.7288**，与射胶量案例 0.6095，语义区分明显。

### 3.4 知识库 BM25 路（PG 关键词路）

**流程**（tools.py:627 `bm25_search`）：

```
query → QueryExtractor 提取 → 中文 2-gram/3-gram 重叠切分（近似分词，无 jieba）
      → 分类：设备词 vs 故障词（_classify_keywords）
      → SQL：每个 token 一个 ILIKE，OR 连接（任一命中即召回）
      → CASE WHEN 加权计分 → 按总分降序
```

**切词示例**：`"注塑机温度过高" → {注塑机, 注塑, 塑机, 温度, 过高}`

**加权计分**（按 token 类别，tools.py:683-694）：

| 类别 | 命中标题 | 命中内容 |
|---|---|---|
| 故障词 | +5 | +2 |
| 设备词 | +1 | +1 |

**为什么**：
- **ILIKE** = PG 大小写不敏感模糊匹配，`%` 通配任意长度，"包含即命中"
- **OR 扩大召回**：只要沾边就捞进来，宁多勿漏——召回阶段允许噪音，由后段过滤清理
- **2-gram 切分**：覆盖复合词变体；**故障词权重大于设备词**（5/2 vs 1/1）：故障描述是相关性最核心的信号，设备只是定位上下文
- SQL 异常时降级为纯 `LIKE` 匹配（健壮性兜底）

**好处**：精确词命中、零延迟、不吃语义模型资源；与向量路互补——**BM25 管"词对上"，向量管"义对上"**。

### 3.5 手册库双路（仅含错误码时启用）

| 路 | 检索方式 | 数据源 | 触发条件 | 特征 |
|---|---|---|---|---|
| ① | 向量（cos） | 知识库 Milvus | 总是 | 语义近似 |
| ② | BM25（关键词） | 知识库 PG | 总是 | 精确关键词 |
| ③ | 错误码精确匹配 | 手册表 `manual_code_entries`（PG） | 仅问题含错误码 | score=1.0，`_dedup_key="M:{id}"`，最高权威 |
| ④ | 手册语义向量 | 手册库 Milvus `log_code` 集合 | 仅问题含错误码 | 同 IVF_FLAT+COSINE |

**③ 精确匹配**（tools.py:779 `manual_code_search`）：`db.query(ManualCodeEntry).filter(error_code.in_(error_codes))`，命中 `score=1.0`，带 `_dedup_key="M:{id}"` 与知识条目（`K:{id}`）区分。
**④ 语义向量**（tools.py:841 `manual_vector_search`）：同一批手册数据编码进 Milvus `log_code` 集合，PG 表存 `milvus_id` 关联（`vector_store.py:509`）。

> **"手册库"不是独立数据库**：`manual_code_entries` 表是同一个 PG 业务库里的一张表（模型 `ManualCodeEntry`，只接受设备说明书/维修手册导入的"错误码→故障诊断"权威映射），④ 的向量是它的 Milvus 副本。

### 3.6 各路召回参数对照

| 路 | 方法 | top_k | 分数含义 | 显示分处理 |
|---|---|---|---|---|
| 向量 | `vector_search` | 10（可传） | 余弦 0~1 | 用作最终展示分 |
| BM25 | `bm25_search` | 10（可传） | 加权命中分（无上限） | 不计入展示分 → 独中条目 0 分 + `rrf_only` |
| 手册精确 | `manual_code_search` | 5 | 1.0（满分） | 计入，融合后置顶 |
| 手册向量 | `manual_vector_search` | 5 | 余弦 | 计入 |

## 4. 融合阶段：RRF 融合（深度专题）

> 代码：`backend/app/agents/tools.py#L472-L583`（`rrf_merge`）
> 作用：把多路检索结果合并成一份排好序的列表。
> 适用：`/hybrid`、`/agent`、`/answer/stream`、`/answer/expert` 的检索融合阶段。
> ⚠️ **路数演进**：早期两路（知识库向量+BM25）；手册库加入后变**双库最多四路**，并新增复合去重键 `_dedup_key` 防撞号（详见第 4.5 节）。下文 4.1~4.4 以两路为例讲解原理，四路扩展规则一致。

### 4.1 核心思想（30 秒版）

RRF（Reciprocal Rank Fusion，倒数排名融合）**不看分数、只看排名**：

```
某条在某路的分 = 1 / (k + 该路名次)      # k = 60（平滑参数）
同一知识双路都命中 → 两份分累加 → 自动排最前
```

**最简例子**：知识库只有 3 条，用户搜"注塑机温度过高"：

| 知识 | 向量路名次 | BM25 路名次 |
|---|---|---|
| **12号** | 第 1 | 第 1 |
| 33号 | 第 2 | 第 2 |
| 45号 | 没召回 | 第 3 |

```
12号 = 1/(60+1) + 1/(60+1) = 0.0328   ← 双路都第一，夺冠
33号 = 1/(60+2) + 1/(60+2) = 0.0322
45号 =           1/(60+3) = 0.0159   ← 只有一路，垫底
```

**结论：双路都认同的知识排最前。** 这就是 RRF 的全部秘密。

### 4.2 为什么不看分数？——量纲不可比

| | 向量路 | BM25 路 |
|---|---|---|
| 分数是什么 | 余弦相似度 | 关键词加权分 |
| 取值范围 | 0 ~ 1（如 0.82） | 无上限（如 5.2） |
| 能直接比吗 | —— | ❌ 口径完全不同 |

两路分数不可比，但"排名"都是"第几"，天然可比。所以 RRF 把分数全扔掉，只比排名。

### 4.3 参数 k=60（有论文依据）

| 名次 | 单路得分 | 双路都命中 |
|---|---|---|
| 第 1 名 | 1/61 ≈ 0.0164 | 0.0328 |
| 第 2 名 | 1/62 ≈ 0.0161 | 0.0322 |
| 第 5 名 | 1/65 ≈ 0.0154 | 0.0308 |
| 第 10 名 | 1/70 ≈ 0.0143 | 0.0286 |

- **k 的作用**：平滑排名差距。排名 1 和排名 2 的分差只有 0.0003，不会"差一名就天差地别"——刻意削弱单路"第一名光环"，**让双路命中的知识有机会胜出**
- **论文依据**：RRF 原论文 *"Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods"*（Cormack, Clarke & Büttcher, ACM SIGIR 2009），pilot 阶段固定 k=60 并在后续验证中不再调整，原文称其 **near-optimal，但 choice was not critical（选值不敏感）**
- **论文表 1（TREC pilot，MAP）**：k=10→0.2123，k=30→0.2139，k=60→0.2145，k=80→0.2147，k=100→0.2142，k=500→0.2098——**60~100 区间 MAP 几乎无差**，k 太大（500）才明显变差
- **事实标准**：该论文后 RRF 成混合检索事实标准，Elasticsearch（8.9 起内置）、Qdrant、Weaviate 等默认 k=60
- **k 的直觉**：k 越小排名靠前独占权重越高；k 越大各名次贡献趋同，**"多条检索路都认可"比"单一路排第一"更重要**——共识效应

### 4.4 三个关键 id（最易混淆，务必先搞懂）

一条知识在系统里存了两份，因此有两套标识：

```
PostgreSQL（正本·档案室）          Milvus（副本·储物柜）
┌──────────────────┐          ┌──────────────────────────┐
│ id: 12 (整数主键) │          │ id: "3f9a..." (UUID 柜号) │
│ 标题/内容...       │          │ knowledge_id: 12 (抄来的学号) │
└──────────────────┘          └──────────────────────────┘
```

| 字段 | 向量路值 | BM25 路值 | 备注 |
|---|---|---|---|
| `item["id"]` | UUID 字符串 | 整数 | 两路口径不一致，**不能当合并键** |
| `item["knowledge_id"]` | 整数 | 整数 | 两路一致 = 身份证号，**合并键** |
| `item["method"]` | `"vector_search"` | `"bm25_search"` | 来源路标签 |

> **比喻**：`knowledge_id` = 学号（两路都有、一致）；`id` = 储物柜号（各编各的）。
> **代码**：`item_id = kid or raw_id` → 优先认学号 → 同一知识合并成一条，双路分才能累加。

**如果不统一去重键会怎样？** 拿 `id` 当合并键 → 同一个 12 号被当成两条 → 双路分合并不上（12 号只有 1/61 而不是 2/61）→ 排序错乱，用户还会看到**两条一模一样的知识卡片**。

#### 4.4.1 第四个 key：`_dedup_key`（双库复合键，防撞号）

手册库加入后，`knowledge_id` 也不够用了——**知识库和手册库的主键都是 PG 自增 int**：

```
知识库（knowledge_items）   id=5  → 《注塑机料筒故障》
手册库（manual_code_entries） id=5  → 《SV0436 伺服放大器过流》
```

两个 id=5 是完全不同的实体，但若按 `knowledge_id` 去重会被当成"双路命中"合并 → **丢条目 / 张冠李戴**。

**解决**：融合前给每条打复合键 `_dedup_key`，用来源前缀隔离：
- 手册条目 → `M:{manual_id}`（如 `M:5`）
- 知识条目 → `K:{knowledge_id}`（如 `K:5`）

合并键优先级：**`_dedup_key` > `knowledge_id` > `id`**。同库内才按 id 判重，跨库永不撞号。

> **类比**：`_dedup_key` = "学校名 + 学号"（清华5号 ≠ 北大5号）；`knowledge_id` = 裸学号（两校都从 1 编起，会撞）。

### 4.5 完整代码走查（9 步）

```python
def rrf_merge(result_sets, k=60, top_n=10):
    scores = {}                                  # ① 记账本
    for result_set in result_sets:               # ② 外层：按"路"循环
        for rank, item in enumerate(result_set, start=1):  # ③ 内层：按"条"循环
            ...                                  # ④ 取id → ⑤ 告警 → ⑥ 打分 → ⑦ 记分 → ⑧ 择优
    merged = sorted(...)                          # ⑨ 排序
    ...                                          # ⑩ 截取 + ⑪ 防御去重
    return unique
```

**Step 1 开记账本**：`scores = {}`，结构 `{知识id: {"rrf": 0.0, "vector_score": 0.0, "item": {...}}}`——`rrf` 排序用内部分（跨路累加）、`vector_score` 展示用分（统一向量相似度 0~1）、`item` 内容模板（保留单路分最高的那份）。

**Step 2 双重循环**：外层一轮 = 一整路；内层一次 = 1 条。循环本身**不产出结果**，只负责记账，结果在循环结束后统一排序产生。

**Step 3 取 id、跳过脏数据**：
```python
raw_id = item.get("id")            # 向量路 → "3f9a..."（UUID）；BM25路 → 12（整数）
kid = item.get("knowledge_id")     # 两路 → 都是 12（数据库主键）
item_id = kid or raw_id            # 优先用 knowledge_id；没有才退回 id
if item_id is None:
    continue                       # 连一个 id 都没有的脏数据 → 跳过不记账
```

**Step 4 一致性告警（哨兵）**：
```python
if raw_id is not None and kid is not None and str(raw_id) != str(kid):
    if method not in _RRF_ALERTED_METHODS:   # 这条路之前告警过吗？
        _RRF_ALERTED_METHODS.add(method)     # 没告警过 → 记下"这条路已提醒过"
        logger.warning(...)                  # 打一条警告日志
```
- **为什么需要 `_RRF_ALERTED_METHODS`**：向量路每条结果都触发该条件（成百上千条），没有它一次融合刷几百条日志；有了它每个方法整次运行只警告 1 次
- **它在保护什么**：对未来的开发者说——"以后新增检索路时如果只带 id 不带 knowledge_id，同一个知识会被当成两条，双路分就合并不了"

**Step 5 RRF 打分 + 累加（双路命中在此实现）**：
```python
rrf_score = 1.0 / (k + rank)             # 公式：名次越靠前，分越高
if item_id not in scores:
    scores[item_id] = {"rrf": 0.0, "vector_score": 0.0, "item": item}
scores[item_id]["rrf"] += rrf_score      # 再见到（另一路）→ 不新建，直接累加
```
**双路命中怎么实现的？——没有专门的判断代码！** 机制 = 外层循环多跑一遍 + 同一个键被再次访问 + `if not in` 区分首/次。

**Step 6 记展示分（只记向量路）**：
```python
if item.get("method") != "bm25_search":    # BM25 的加权分（5.2）展示给用户会懵
    item_sim = item.get("score", 0)
    if item_sim > scores[item_id]["vector_score"]:
        scores[item_id]["vector_score"] = item_sim
```
展示分永远只记向量余弦相似度（0~1），BM25 独中条目 `vector_score=0` → 标记 `rrf_only=True`。

**Step 7 保留最佳详情（择优不是多存）**：`if item_score > scores[item_id]["item"].get("score", 0): scores[item_id]["item"] = item`——每个知识永远只有 1 个 item（内容模板）。

**Step 8 排序 + 截取**：`merged = sorted(scores.values(), key=lambda x: x["rrf"], reverse=True)` → 取 `merged[:top_n]` → `item["score"] = vector_score`（展示分覆盖）→ `item["rrf_only"] = vector_score <= 0`。

**Step 9 防御性去重**：返回前按 `knowledge_id or id` 再清一遍（双保险）。正常情况 Step 5 已按 knowledge_id 合并不会重复；万一未来某路用了不稳定 id 漏网，这里兜底，**确保返回列表绝不含两条同一知识**。

### 4.6 完整示例走查（带账单变化）

输入：向量路 2 条（12号 0.82、33号 0.61）+ BM25 路 3 条（12号 5.2、33号 3.1、45号 2.0）：

| 步骤 | 处理条目 | scores[12] | scores[33] | scores[45] |
|---|---|---|---|---|
| ① 向量路 12号 | 新建 | rrf=0.0164, vs=0.82 | —— | —— |
| ② 向量路 33号 | 新建 | 同上 | rrf=0.0161, vs=0.61 | —— |
| ③ BM25 12号 | 累加 | rrf=**0.0328**, item 换 BM25版 | —— | —— |
| ④ BM25 33号 | 累加 | —— | rrf=**0.0322**, item 换 BM25版 | —— |
| ⑤ BM25 45号 | 新建 | —— | —— | rrf=0.0159, vs=0, item=BM25版 |

最终输出：12号(0.0328, score=0.82) > 33号(0.0322, 0.61) > 45号(0.0159, **0.0**, rrf_only=True ← BM25 独中，会被下游过滤)。

### 4.7 双库四路融合与错误码置顶

#### 4.7.1 不是 4 个库，是 2 个库最多 4 路

```
                    ┌─ 知识库（knowledge） ① 向量检索（cos，Milvus）
                    │                      ② BM25 关键词检索
   问题 ── 提取错误码 ┤
  （含错误码才走③④）│ 手册库（log_code）  ③ 错误码精确匹配（查 PG 表，非向量）
                    │                      ④ 手册语义向量（Milvus）
                    └─ 全部路 → rrf_merge（按名次，最多 4 个 result_set）
```

普通问题（无错误码）：2 路进融合；报错误码（如 SV0436）：4 路进融合。

#### 4.7.2 四路 RRF 累加示例（双库各自双路命中）

```
问题"机床报 SV0436 伺服过流"
知识案例《X轴过载报警》   ① 向量第1 + ② BM25第2 → 1/61 + 1/62        ← 知识库双路命中
手册条目《SV0436 过流》   ③ 精确第1 + ④ 向量第1 → 1/61 + 1/61 + 置顶  ← 手册库双路命中
```

同一条目四路全命中时 RRF 分最高可达 4 路累加；跨库条目由 `_dedup_key` 隔离各自计分。

#### 4.7.3 错误码精确匹配置顶修正（关键）

RRF 按名次融合后，③ 路的权威手册条目（score=1.0）只在单路出现，会被知识库双路命中的泛案例挤下去。在 `filter_rerank_cases` 输出前按：

```python
sorted(key=lambda x: (0 if x.get("method") == "manual_code_exact" else 1, -x.get("score", 0)))
```

把 `manual_code_exact` 条目提到最前，其余按匹配度降序——**保证"错误码精确命中"永远排第一**，因为它是设备手册的权威标准处理，优先级高于知识库相似案例。

### 4.8 边界情况

| 场景 | 行为 |
|---|---|
| 知识只出现在一路 | 只有 1/(k+rank) 分，`vector_score=0` → `rrf_only=True` → 下游过滤 |
| 同一知识在两路名次不同 | 12号向量第1、BM25第5 → 1/61+1/65=0.0318，仍高于单路第1的 0.0164 |
| 脏数据（无 id 无 knowledge_id） | `item_id=None` → Step 3 `continue` 跳过，不崩、不污染账单 |
| 只有一路返回成功 | 外层只循环 1 次 → 等价单路按名次排序，RRF 退化为普通排名 |
| 双库 id 撞号 | 用 `_dedup_key`（`K:5`/`M:5`）互不干扰，各自独立计分 |
| 手册精确匹配只出现在一路 | 名次吃亏是 RRF 名次融合的固有倾向，非 bug → 下游置顶修正 |

### 4.9 常见疑问速查

| 疑问 | 答案 |
|---|---|
| 双路命中怎么判断的？ | 没有专门代码。外层循环第二轮碰到同键 → `if item_id not in scores` 区分首/次 → 累加 |
| 一次循环记了向量又记关键字？ | 不是。一次迭代只处理一路的一条；`vector_score` 用 `method != "bm25_search"` 过滤 |
| 每轮循环找到几条？ | 外层一轮 = 一路全部条目（多条）；内层一次 = 1 条（记账） |
| 每次循环算一条结果吗？ | 是"记账一条"，不是"产出结果一条"；结果在循环结束后统一排序产生 |
| 保留多少条？ | scores 每知识 1 条 → RRF 前 top_n（默认 10）→ 严格过滤后再筛到 8 |
| 知识库已去重为何还去重？ | 录入去重防"存重"；RRF 去重防"查重"（一次搜索两路各返回一份，合并成一条） |
| id / knowledge_id 啥关系？ | `knowledge_id`=数据库主键（身份证），`id`=两路各发各的（柜号），用 kid 合并 |
| 融合输入是筛选过的吗？ | 是两路各自召回 top_k 的候选集；相关度筛选在融合之后（score≥0.15） |
| rrf_only 是什么？ | 只有 BM25 命中、无语义匹配的标记，下游会过滤掉 |
| k=60 能改吗？ | 能，但一般不用改。k 越大名次间分差越小（越平滑） |

## 5. 精排阶段：过滤 + 加权重排 + 严格过滤

> 统一入口：`retrieval_flow.py` 的 `filter_rerank_cases()`（L103），问答/专家/钉钉共用。
> 顺序：过滤 rrf_only/低分 → 加权重排 → 设备/故障关键词严格过滤 → 错误码置顶 → 截取。

### 5.1 基础过滤：剔除 `rrf_only` 且 score < 0.15

```python
filtered = [m for m in merged if not m.get("rrf_only", False) and m.get("score", 0) >= 0.15]
```

- `rrf_only=True` = 该知识**只有 BM25 命中、向量路没有召回**（显示分=0）——"关键词碰巧撞上，但语义上向量路不认可"，是 OR 召回捞进来的典型噪音
- 向量分 < 0.15 = 语义几乎不相关
- **好处**：用"向量语义认可"作为硬门槛，把关键词撞车的假命中挡在门外

### 5.2 加权重排 `weighted_rerank`（tools.py:322）

**怎么计算**：

1. 从提取词中分离两类（`_DEVICE_TYPE_TERMS` 硬编码设备词 + `cleaned_query` 拆分）：
   ```
   device_kw = {注塑机}          ← 命中硬编码设备词表
   fault_kw  = {温度, 过高}      ← 剩余技术词（剔除通用词"故障"及 device_kw），兜底用 _FAULT_CAUSE_SIGNALS
   ```
2. 对每条候选算两个指标：
   ```
   fault_hit_count = fault_kw 中出现在 标题+正文(+error_code) 的词个数   ← 子串包含匹配，每词最多计 1 次
   fault_ratio     = fault_hit_count / len(fault_kw)                    ← 覆盖率（分母是查询词数，跨查询可比）
   device_match    = 该条 device_type 是否包含 device_kw 的词
   ```
   （手册条目正文不含错误码本身，须把 `error_code` 纳入命中匹配，否则"SV0436"提问无法命中手册条目——tools.py:391-394）
3. 三分支修正（基数为 RRF 后的向量余弦分）：

| 条件 | 公式 | 含义 |
|---|---|---|
| 设备不匹配 | `×0.2` | 设备都对不上，语义再近也不可信（硬惩罚） |
| 故障命中 0 或 ratio < 0.3 | `×0.15` | 只沾边、实质无关 → 压到地板 |
| ratio ≥ 0.3 | `×(1 + 0.4×ratio)`，上限 1.0 | 故障概念覆盖越多加越多，最多 +40% |

> **注意一个易混淆点**：`weighted_rerank` 的签名参数 `device_penalty=0.15` 是"保留未使用"的（docstring 已注明），实际设备不匹配惩罚是**硬编码 ×0.2**（tools.py:412）。别被参数名误导。

**为什么这样计算**：
- **RRF 只认排名丢了分数**，这一步拿回真实相关度做精细校正
- **设备是门槛、故障是增益**：设备不匹配直接 ×0.2，故障命中只在上限内加分
- **用比率不用绝对数**（标准做法）：查询故障词数量不等（2 个 vs 4 个），绝对命中数不可比，归一化后才跨查询可比
- **0.3 / 0.4 / 0.15 三个系数**是项目结合业务调出的启发式经验值，无权威标准，属于"有依据的经验设计"
- **上限 1.0**：防止加分超过语义余弦理论上界

**实测效果**："模具温度失控"命中故障词 1/2 → `0.7288 × 1.2 = 0.8746`；射胶量/电机异响命中 0 个 → `0.6095×0.15=0.0914`、`0.5677×0.15=0.0852`，胜负立判。

**效率与架构（为什么这么快）**：
- 重排只对比**过滤后的几条候选**，不是全库——前面的双路召回 + RRF + 过滤已把范围收窄
- 每条成本 = Python 子串匹配（微秒级）；实测 RRF 融合 + 重排合计 **2.6ms**
- 这是标准的**两阶段检索架构**：粗排（召回：广撒网、快）→ 精排（重排：精细、贵计算给最少候选）

### 5.3 严格过滤 `filter_rerank_cases`（问答/专家模式额外）

在基础过滤 + 重排之上，问答（`/answer/stream`）与专家（`/answer/expert`）再叠加一层"设备 + 故障关键词"严格过滤：

1. 用 `query_extractor` 白名单从提问提取设备类型（`_DEVICE_TYPE_TERMS` 最长词优先）和故障关键词（剔除设备词后的技术词）
2. 案例必须**设备类型精确匹配**（`m.get("device_type") == require_device`）且**标题/正文/错误码至少命中一个故障关键词**（`retrieval_flow.py:131-141`），否则剔除
3. **严格过滤为空 → 回退宽松过滤的 top2**（防止误伤导致"未检索到"，`retrieval_flow.py:143-145`）

作用：剔除跨设备案例（如"数控机床主轴过热"误召回"输送设备电机过热"）和同设备泛相似案例（如"黑屏"），**根治多故障提问的串味问题**。

> 兜底分支已通过初始 0.15 过滤，不再二次过滤（重排可能压低分数），直接返回 top_n——`retrieval_flow.py:156-158` 的注释说明了这个细节。

### 5.4 错误码置顶（最后一步）

有错误码时，`method == "manual_code_exact"` 的条目在严格过滤后置顶（详见第 4.7.3 节），然后按 `score >= 0.15` 再过滤一次并截取 top_n。

## 6. 输出与 LLM 生成

### 6.1 各入口 TopN 取值

> 规律：**注入 LLM 的少而精，展示给用户浏览的多**。

| 入口 | 重排后取几条 | 代码位置 | 用途 | 为什么这个数 |
|---|---|---|---|---|
| 追踪维修 `_search_knowledge` | **3 条** | `merged[:3]`（guided_repair_agent.py:203） | Top3 注入 LLM 生成下一步排查 | 对话式引导只需最相关的几条，多了干扰 LLM 判断 |
| 钉钉知识检索 `search_knowledge` | **5 条** | `filter_rerank_cases(top_n=5)`（mcp/tools.py:88） | Top5 交给 AnswerAgent 生成回答 | 回答要综合参考，稍多几条 |
| 问答 `/answer/stream` | **最多 8 条** | `filter_rerank_cases`：严格过滤后截前 8 | 注入 LLM + 用户浏览 | 供 LLM 参考要少而精，且剔除串味案例 |
| 专家 `/answer/expert` | **每故障 ≤8 条** | 各子查询走 `filter_rerank_cases`，跨故障全局按分数降序取 8 | 分组回答 + 用户浏览 | 多故障分组检索，展示时全局降序 |
| 搜索页 `/search/agent` | **top_k 条**（前端默认 8） | `rrf_merge(top_n=request.top_k)`，不额外截断 | 展示给用户浏览的案例列表 | 用户要浏览多条 |

### 6.2 Prompt 注入与"只引用案例"约束

- 重排后取前 N 条，content 截断 600 字
- 作为"知识库参考（唯一知识来源）"注入 Prompt
- 强制 LLM：**只能引用案例明确写到的内容**（灯名/部件名/数值不得补充），未检索到则如实回"知识库暂无相关案例"——这是项目最关键的约束：**案例来源必须是真实工单，不能是 AI 生成的**
- 实测：AI 回复中"模温机显示温度与实际偏差>10℃"与该案例内容逐字一致，未自由发挥

## 7. 检索入口详解：ReAct 循环检索（/agent）

> 代码：`backend/app/agents/retrieval_agent.py`（`RetrievalAssistantAgent`）
> 端点：`POST /api/v1/search/agent`（search.py:176）→ `RetrievalAssistantAgent.search()`
> 前端：Search.vue（页面名"AI 知识问答"）

### 7.1 是什么

ReAct = **Reason（思考）→ Act（行动）→ Observe（观察）** 的迭代循环。
让 LLM 当"决策者"，**自主决定每一步查什么**：查不到就换策略/改写查询再查，直到结果满意或到达轮次上限。

与"固定管道"检索的本质区别：

| | 固定双路检索 | ReAct 循环检索 |
|---|---|---|
| 决策者 | 代码写死（向量+BM25 各查一次） | **LLM 每轮自主选择工具** |
| 查询 | 只用原始查询 | 结果差时 `rewrite_query` 改写再查 |
| 记忆 | 无 | scratchpad 记录每轮"思考/行动/观察" |
| 停止条件 | 一次跑完 | 质量达标 / LLM 选 finish / 5 轮上限 |

**比喻**：普通检索像"固定查两步"；ReAct 像老师傅查资料——第一次没查到 → 换个说法再查 → 换个角度查关联 → 按故障码精确筛，每步基于上一步结果决策，最多试 5 种办法，够了就收手。

### 7.2 循环结构

```
for 迭代 in 1..MAX_ITERATIONS(=5):
    │
    ├─ ① 思考 _think       LLM 查看「当前查询 + 已获结果摘要 + 推理历史(scratchpad)」
    │                        → 决定下一步行动（JSON：action + 参数）
    │
    ├─ ② 行动              执行选定的检索工具（或改写查询、或宣布完成）
    │
    ├─ ③ 观察              记录本步结果，按 knowledge_id 去重累计进 all_results
    │
    └─ ④ 判断 _evaluate_quality
            达标 → break
            未达标（1~4 轮）→ 回到 ①
            第 5 轮 → 强制达标 break
收尾：多路结果 RRF 融合排序 → 返回
```

### 7.3 每轮的质量公式（规则判断，不用 LLM，省一次调用）

代码 [retrieval_agent.py:404-420](file:///d:/Smart-Repair-System/backend/app/agents/retrieval_agent.py#L404-L420)：

```python
if len(results) == 0:
    return insufficient("无结果")
high_score_count = count(score >= 0.6)          # 高分条数（MIN_SCORE_FOR_QUALITY）
max_score = max(score)                          # 最高分
if len(results) >= 3 and (high_score_count >= 2 or max_score >= 0.7):
    return sufficient("结果充足")                # ★ 达标
if iteration >= 5:
    return sufficient("达到最大迭代次数")        # 到点强制交货
return insufficient("结果不足")
```

**达标标准（精确）**：结果 **≥3 条**，且满足任一：
- 至少 **2 条** 分数 ≥0.6；或
- **1 条** 最高分 ≥0.7

**设计意图**：
- 分数来自向量余弦 / RRF 分，即"语义上足够像"才算数——**光凑够 3 条低分案例不达标**
- "是否收手"由**规则公式把关**，不由 LLM 说了算——防止 LLM 偷懒提前结束或无限查下去

### 7.4 可选策略（6 种）

枚举定义 [retrieval_agent.py:21-28](file:///d:/Smart-Repair-System/backend/app/agents/retrieval_agent.py#L21-L28)：

| 策略 | 用途 | 适合场景 | 可带参数 |
|---|---|---|---|
| `vector_search` | 向量语义检索 | 模糊/口语化描述，按意思匹配 | top_k、score_threshold |
| `bm25_search` | 关键词精确检索 | 含明确关键词/故障码/设备编号 | top_k |
| `conditional_query` | 条件精确筛选 | 已确定设备类型/故障码/标签，按字段过滤 | device_type、fault_code、keyword |
| `graph_query` | 关联查询 | 查与某设备/故障相关的周边知识 | device_type、fault_code、top_k、exclude_ids（自动排除已查到的） |
| `rewrite_query` | 查询改写 | 结果不足时改写成更专业表述再查 | strategy（如 expand_synonyms） |
| `finish` | 完成 | 结果足够或不想查了 | — |

**LLM 的决策原则**（写死在 system_prompt，retrieval_agent.py:324-345）：
- 语义模糊 → `vector_search`；关键词明确 → `bm25_search`
- 用户给了设备/故障码 → 可追加 `conditional_query` / `graph_query`
- 首轮建议 vector + bm25 并行
- 质量不足**且有结果** → prompt 强制提示改用 `rewrite_query` 重试

**降级兜底 `_fallback_decision`**（retrieval_agent.py:395-402，LLM 思考返回非法 JSON 时）：
- 首轮 → 固定执行 `vector_search`（降级策略）
- 已有结果但不足 → 自动改 `rewrite_query` 重试
- 无结果 / 已到第 5 轮 → 自动 `finish`
- LLM 配置带 `timeout=30, max_retries=1`——**LLM 挂了也不能让整个检索崩掉**

### 7.5 结束方式（3 种）与"超轮不失败"

| 结束方式 | 触发条件 | 返回内容 |
|---|---|---|
| 质量达标 | ≥3 条 且（2 条≥0.6 或 1 条≥0.7） | 全部累计结果（RRF 融合排序） |
| 提前收手 | LLM 自主选 `finish` | 同上 |
| 到点交货 | 5 轮跑满，强制判达标 | **前几轮累计的所有结果**，照常返回 |

**不会因为超轮次而报失败**——"5 轮是耐心上限，不是失败上限"。
- 有结果（哪怕 1 条）：正常返回案例列表
- 完全没查到：返回空列表 → 前端友好提示"未找到相关案例，建议换关键词/补充型号或故障码"

真正的失败路径只有两条：LLM 思考失败（自动降级，不失败）、查询改写失败（返回改写前已累计的结果）。

### 7.6 `require_hybrid` 强制混合（关键优化）

**问题**：ReAct 第一轮选 `vector_search` 且质量达标就早停，导致"混合检索"名存实亡。

**解决**（retrieval_agent.py:117-147）：`require_hybrid=True` 时，首轮**确定性执行 vector + BM25 双路检索**（不走 LLM 决策），双路结果质量达标直接进 RRF 融合；不达标才进入 LLM 决策循环。专家模式（`/answer/expert`）首轮即开启（search.py:435 / 478）。

### 7.7 页面展示的独特产出

ReAct 独有的输出（`RetrievalResult`，retrieval_agent.py:41-50）：
- `strategies_used`：实际用过的检索策略名
- `rewrite_count`：查询被改写了几次
- `rewritten_queries`：改写出的新查询词
- `scratchpad`：完整推理链路（思考/行动/观察），调试用
- `total_time_ms`：总耗时

### 7.8 与其他入口的分工与定位

| 入口 | 定位 | 检索方式 |
|---|---|---|
| AI 知识问答（Search.vue） | 一次性捞历史案例、**可追溯** | ReAct 循环 |
| 智能问答（AiAssistant / /answer） | 直接给结论式回答 | 固定双路 + AnswerAgent |
| 追踪维修 | 一步步引导排查 | 轻量双路 + GuidedRepairAgent |
| 钉钉机器人 | 移动端快捷入口 | robot_graph 按意图分发 |

> 注意：四者**共用同一个知识库**（PG `knowledge_items` + Milvus），差异只在检索流程复杂度与 Agent 分工。

**ReAct 在本项目的作用**：
1. 让模糊口语（"那台机器老报警"）也能查到案例——`rewrite_query` 改写成专业表述
2. 查得全、查得准——LLM 动态换策略 + 明确质量达标线
3. 结果可追溯可核验——展示策略、改写次数、案例来源卡片，不是黑盒结论

**设计哲学**：搜索页要"查得全、查得准"（用 ReAct 多轮试错）；问答/追踪维修要"快、稳、不超时"（用固定双路）。两套检索共用同一份知识库与同一套 RRF/重排算法。

## 8. 性能保障：索引与缓存

### 8.1 Milvus 向量索引（IVF_FLAT + COSINE）

> 代码：`backend/app/core/vector_store.py#L136-L150`（基类 `_create_index`，两个集合共用）

```python
index_params = {
    "index_type": "IVF_FLAT",
    "metric_type": "COSINE",
    "params": {"nlist": 1024}
}
```

**为什么需要索引**：Milvus 存的是 1024 维向量，暴力全库算相似度在数据量上来后不可接受。需要**近似最近邻（ANN）索引**：牺牲一点点精度，换取几十上百倍加速。

**IVF_FLAT 原理（倒排文件 + 暴力精排）**：
```
建库（写入时）：KMeans 聚成 nlist 个簇 → 每向量进最近簇 → 建"簇→向量列表"倒排索引
查询：算查询向量与 nlist 个簇中心的距离 → 只进最近 nprobe 个簇（候选区）
      → 候选区内暴力算余弦精排 → 返回 top_k
```

**FLAT 的含义**：候选区内计算精确（不压缩向量），不像 IVF_PQ/IVF_SQ8 有量化损失——"索引加速 + 结果无损"。

**两个关键参数**：

| 参数 | 含义 | 本项目取值 | 权衡 |
|---|---|---|---|
| `nlist` | 建库时分多少簇 | 1024 | 越大候选区越细，但建库慢 |
| `nprobe` | 查询时搜几个簇 | 16 | 越大召回越全越慢；越小越快可能漏 |

nprobe=16 / nlist=1024：每次只搜全库 16/1024 ≈ 1.5% 的数据，毫秒级响应。

**为什么选 COSINE**：Qwen3 编码后已 L2 归一化，COSINE 只关心方向、不关心长度——语义相似度场景方向一致 = 语义相近；归一化后 COSINE 与 L2 数学上等价（`|A-B|² = 2-2cos(A,B)`），但 COSINE 语义更直观。

**两个集合的用法**：

| 集合 | 存什么 | 检索入口 | 额外标量过滤 |
|---|---|---|---|
| `knowledge` | 知识条目 | `KnowledgeVectorStore.search`（vector_store.py:211） | `device_type` / `fault_code` 表达式 |
| `log_code` | 手册错误码 | `LogCodeVectorStore.search`（vector_store.py:509） | `device_type` / `error_code` 表达式 |

两个 search 都支持 `expr` 标量过滤表达式（如 `device_type == "注塑机"`），实现"先按条件过滤候选、再向量精排"。

### 8.2 PG pg_trgm 索引（BM25 路）

> 目标：让 `ILIKE '%关键词%'` 模糊匹配在上千条知识后依然毫秒级，避免退化为全表扫描。
> Migration：`7a8b9c0d1e2f_add_pg_trgm_indexes.py`（2026-08-05，可回滚）。

**为什么做（问题背景）**：
- BM25 的 SQL 是 `title ILIKE '%词%' OR content ILIKE '%词%'`——`%词%` 意味着"任意位置包含"，位置不确定
- 没有索引时，PostgreSQL 只能**逐行全文扫描**（O(n)）：几百条时毫秒级无感，到**上万条会明显变慢**
- 向量路靠 Milvus ANN 索引天然可扩展，**BM25 是全链路唯一随数据量恶化的环节**，必须提前铺路

**为什么普通索引不行**：B-tree 只擅长"精确值/前缀"匹配（`title='xx'` 或 `LIKE 'xx%'`），对中间的 `%xx%` 无能为力。需要专门为"子串包含匹配"设计的工具：**pg_trgm**。

**怎么实现（原理）**：
1. 建索引时：把每段文本切成**连续的 3 字片段（trigram）**
   ```
   "注塑机温度过高" → 注塑机, 塑机温, 机温度, 温度过, 度过高
   ```
2. 用 **GIN 倒排索引**登记：每个 trigram → 包含它的所有行号
   ```
   "注塑机" → {第5行, 第89行, ...}
   ```
3. 查询时：查询词切 trigram → 查倒排索引直接拿候选行号（哈希定位 O(1)）→ 只对候选行做精确 ILIKE 验证（防假命中）
   ```
   10000 行全扫  →  索引锁定几十行候选  →  只验证这几行
   ```

**实现细节（已落地）**：
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_knowledge_title_trgm ON knowledge_items USING gin (title gin_trgm_ops);
CREATE INDEX idx_knowledge_content_trgm ON knowledge_items USING gin (content gin_trgm_ops);
```
- 已验证：强制走索引时执行计划显示 `Bitmap Index Scan on idx_knowledge_title_trgm / idx_knowledge_content_trgm`
- downgrade 只删索引、保留 extension（可能被其他地方依赖）

**边界与注意**：
- **查询词 ≥3 字提速最明显**（有 trigram 可拆）；2 字词（如"温度"）没有 trigram，会部分退化——BM25 的 2-gram/3-gram 混合切词恰好长短互补
- **数据量小时优化器自动选全表扫描**——全扫比索引便宜，这是正常的（当时约 25 条时就是全扫）；数据量上千后优化器会**自动**改用 Bitmap Index Scan，无需改动代码

**益处**：
- 查询复杂度从 **O(n) 降到 O(候选集)**，数据越多差距越大
- 写入代价极小（每次插入只登记几个 trigram）；知识库"读多写少"，非常划算
- 与向量路的 Milvus ANN 索引形成对称：**两条检索路都有索引支撑，数据增长不拖累任何一路**

## 9. 已知问题与修复记录

### 9.1 RRF 合并键不一致 Bug（已修复）

**问题**：早期 `rrf_merge` 用 `id` 做合并键，但：
- 向量路的 `id` = Milvus point_id（uuid 字符串）
- BM25 路的 `id` = 数据库知识 id（整数）

同一知识两路 `id` 不同 → 被当成两条，**双路命中分不合并**（实测模具温度失控拆成 0.0164+0.0161，而非合并的 0.0325），排序精度受损。

**修复**：合并键改为优先 `knowledge_id`（知识库主键，跨路稳定）。

**防范措施**：
1. **一致性告警**：某路返回的 `id` 与 `knowledge_id` 不一致时打 WARNING（每路仅一次，`_RRF_ALERTED_METHODS`），提示新增检索路必须带 `knowledge_id`
2. **防御性去重**：返回前兜底按 `knowledge_id` 去重，防止未来回归
3. **docstring 写明去重键约定**，维护者一看便知

### 9.2 双库 id 撞号（手册库加入后的新坑，已解决）

知识库与手册库主键都是 PG 自增 int（都从 1 开始），按 `knowledge_id` 去重会撞号。解决：`_dedup_key` 复合键（`K:{id}` / `M:{id}`）隔离来源（详见第 4.4.1 节）。

### 9.3 手册精确匹配名次吃亏（已解决）

③ 路权威条目（score=1.0）只在一路出现，RRF 按名次算会被知识库泛案例挤下去。解决：融合过滤后按 `method == manual_code_exact` 置顶（详见第 4.7.3 节）。

### 9.4 检索逻辑策略漂移（已重构）

早期"检索逻辑写多遍"（搜索页 / 问答 / 钉钉各写一套）导致策略漂移。解决：抽取公共编排层 `retrieval_flow.py`（`retrieve_hybrid` + `filter_rerank_cases` + `make_tools`），所有入口共用唯一实现。

### 9.5 ReAct 首轮早停导致混合检索名存实亡（已解决）

ReAct 第一轮选 vector 且达标就早停，双路检索失去意义。解决：`require_hybrid` 强制首轮确定性执行 vector+BM25 双路（详见第 7.6 节）。

### 9.6 已知边界（不打算修）

- **错误码漏判**：非规范格式错误码提取不到 → 走 2 路，不启用手册权威答案（正则方案的设计取舍）
- **2 字查询词 BM25 部分退化**：无 trigram 可拆，靠 2-gram 词 ILIKE 兜底

### 10.1 检索链路参数

| 参数 | 值 | 位置 | 含义 | 取值依据 |
|---|---|---|---|---|
| RRF 平滑系数 k | 60 | `rrf_merge` | 排名→分数映射斜率 | ① Cormack 等 SIGIR 2009 论文 pilot 固定值，60~100 近最优；② ES/Qdrant 等默认值 |
| 向量召回阈值 | 0.0 | `vector_search` | 语义最低线 | ④ 召回阶段宁多勿漏，交给下游过滤 |
| 过滤阈值 | 0.15 | `filter_rerank_cases` | 语义认可门槛 | ④ 经验值：余弦 <0.15 视为基本无关 |
| 设备不匹配惩罚 | ×0.2 | `weighted_rerank`（硬编码 L412） | 硬惩罚 | ③ 设备类型都对不上，可信度削 80% |
| 故障低命中惩罚 | ×0.15 | `weighted_rerank` | 压到地板 | ③ 接近归零（保留极小分避免系统性误杀） |
| 故障命中增益 | ×(1+0.4×ratio) | `weighted_rerank` | 最多 +40% | ③ 项目既定加权公式 |
| 覆盖率断点 | 0.3 | `weighted_rerank` | ≥30% 才给正反馈 | ④ 经验值：覆盖不足 1/3 概念视为基本不相关 |
| 故障词权重（标题/内容） | 5 / 2 | `bm25_search` | 故障命中加分 | ③ 故障描述是相关性核心信号；标题比正文凝练更可信 |
| 设备词权重（标题/内容） | 1 / 1 | `bm25_search` | 设备命中加分 | ③ 设备只是定位上下文，权重刻意压低 |

## 11. 规模增长调优路线（前瞻）

> 面向知识库规模增长的前瞻性调优方案。
> 当前阶段（知识量小）不做改动，本文档作为后续优化的方向性指引。
> 触发时机用"观察信号"驱动，不提前过度设计。

### 11.1 规模增长带来的预期问题

| 问题 | 现象 | 根因 |
|---|---|---|
| 阈值失真 | 固定 0.15 无法区分"没查到"和"查到但不相关" | 案例变多后分数分布变化 |
| 改写策略单一 | 一种改写法救不回"没查到"的多种原因 | 模糊、黑话、分类宽等不同失败原因 |
| 召回不足 | top-8 可能错过正确案例 | 相关案例变多，一步到位截断太早 |
| 检索变慢 | Milvus / PostgreSQL 查询耗时上升 | 数据量增大，索引未同步优化 |
| 区分度下降 | 相似案例过多，分数挤在一起 | 近似知识重复增长 |

### 11.2 方向一：轻量兜底方案演进

**现状（拟定）**：`/answer/stream` 检索后判断，最高分 < 0.15 时用 LLM 改写查询重试一次（只多 0~1 次 LLM 调用，成本低）。

- **演进 A：阈值动态化**——固定阈值 → 按查询类型分：精确查询（含故障码/编号）threshold=0.30；模糊语义查询 → 动态百分位（如 P30）
- **演进 B：改写策略多样化**——一次改写生成多条候选查询并行重试：同义词扩展 / 设备类型收窄 / 拆分长句
- **演进 C：止损判断**——重试一次仍无结果时，明确回复"知识库暂未收录，建议补充知识"，避免无限改写浪费成本

### 11.3 方向二：两阶段检索（核心）

规模变大后，核心矛盾从"查不到"变为"查不准"。方案：**先多召回、再精排**。

```
阶段一（粗排）：Milvus + BM25 各召回 top 50~100 → RRF 融合
阶段二（精排）：对粗排结果精细重排 → 取 top 5~8 喂 LLM
```

> 衔接说明：项目**当前已是"小规模两阶段"**（召回 top5~10 → 精排取 top3~8，见第 5.2 节"效率与架构"）；
> 这里的"召回扩到 50"是数据量增大后对粗排阶段的扩容，架构思路一脉相承。

精排手段可选（按投入成本排序）：
1. 升级现有 `weighted_rerank`（规则调参，成本最低）
2. Cross-Encoder 重排（"问题×案例"联合编码打分，更准但慢，适合精排阶段）
3. LLM 挑选（让 LLM 从粗排结果中挑最相关的 5 条，即"决策一体化"的轻量版）

### 11.4 方向三：索引层面

| 存储 | 现状 | 规模变大后的调整 |
|---|---|---|
| PostgreSQL | 已有 pg_trgm GIN 索引（migration `7a8b9c0d1e2f`） | 确认索引实际生效；按需分区（按设备类型/时间） |
| Milvus | **IVF_FLAT + COSINE（nlist=1024，nprobe=16）** | 调优 nlist/nprobe（数据量增大可考虑 HNSW）；用 `device_type`/`fault_code` 标量字段做分区过滤 |

> ⚠️ **勘误**：原《检索调优路线.md》此处写"Milvus：HNSW 索引"与代码不符——当前代码实际是 **IVF_FLAT**（`vector_store.py:136-150`）。已在本整合文档中修正，HNSW 仅作为规模更大后的候选方向。

### 11.5 方向四：分面预过滤

知识库变大后，检索前先**收窄范围再搜**：

- 请求已带 `device_type` / `fault_code` 可选字段（`AnswerRequest` / `SearchRequest`）
- 后端先按设备类型过滤子集 → 再向量检索（`vector_store.search` 已支持 `expr` 标量过滤）
- 收益：搜得快 + 更准
- 现状：字段已定义但前端基本未用，属于"低成本高收益"项

### 11.6 方向五：缓存层

高频问题（重复故障现象）走 Redis 缓存：

```
question + device_type → 检索结果缓存
知识库版本号变更 → 缓存失效
```

- 减少重复查询的 Milvus / LLM 消耗
- 依赖现有 `cache_service.py`（Redis，端口 7379）

### 11.7 调优优先级建议

| 优先级 | 事项 | 收益 | 成本 |
|---|---|---|---|
| 1 | 两阶段检索（召回扩到 50，精排选 8） | 高（解决"查不准"） | 中 |
| 2 | 动态阈值 + 多策略改写（兜底升级） | 中（解决"查不到"） | 低 |
| 3 | 分面预过滤（device_type/fault_code） | 中（提速 + 提准） | 低 |
| 4 | 缓存层（Redis） | 中（省成本） | 低 |
| 5 | 索引调优（IVF_FLAT 参数 / pg_trgm / 分区） | 中（保持速度） | 低~中 |
| 6 | 完全体一体化（LLM 决策 + 混合检索 + LLM 回答） | 边际收益小 | 高（延迟/成本大） |

> **结论**：**默认链路不建议做完全体一体化**。它让每次问答多 2~6 次 LLM 调用，延迟从几秒飙到 10~30 秒，而检索层已有的规则优化已覆盖大部分收益。
>
> 但该路径的可行性已被**专家模式**验证：对复合/复杂问题做"选择性一体化"——用户主动切专家模式才触发，普通问答仍走快速链路。**原则：一体化只做用户主动触发的少数场景，不做默认全量**。

### 11.8 触发时机

| 观察信号 | 建议动作 |
|---|---|
| 用户反馈"问答查不到东西"，日志显示检索最高分普遍偏低 | 做优先级 2（动态阈值 + 多策略改写） |
| 用户反馈"答不到点子"，实际是召回不足（top-8 漏掉正确案例） | 做优先级 1（两阶段检索） |
| 检索接口 P95 延迟明显上升 | 做优先级 3/5（分面 + 索引） |
| DeepSeek/Milvus 调用成本升高 | 做优先级 4（缓存） |

> 核心原则：**用观察信号驱动，不提前过度设计**。当前阶段保持现状即可。
