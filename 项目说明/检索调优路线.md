# 知识检索调优路线

> 面向知识库规模增长的前瞻性调优方案。
> 当前阶段（知识量小）不做改动，本文档作为后续优化的方向性指引。

---

## 一、现状梳理

### 1.1 当前主链路

| 链路 | 组合方式 | 场景 | 特点 |
|---|---|---|---|
| `/agent`（组合①） | LLM 决策 + 混合检索 | 知识搜索页 | 质量优先，慢，只查不答 |
| `/answer/stream`（组合②） | 固定混合检索 + 严格过滤 + LLM 生成回答 | 智能问答页、工单 AI 弹窗 | 速度快，查完再答；多故障提问提示切专家模式 |
| `/answer/expert`（组合③） | 多故障拆解 + 并行 ReAct（强制双路）+ 分组回答 | 智能问答页·专家模式 | 复杂 / 复合问题逐故障深挖 |

> 注：问答（②）与专家（③）共用 `require_hybrid` 强制混合检索与 `_filter_rerank_cases` 严格过滤（设备精确匹配 + 故障关键词命中）。

### 1.2 检索链路已用的优化手段

| 手段 | 作用 | 位置 |
|---|---|---|
| `query_extractor` 白名单提取 | 免 LLM 的关键词清洗 | `agents/query_extractor.py` |
| 双路召回（Milvus + PG BM25） | 语义 + 关键词互补 | `agents/tools.py` |
| RRF 融合 | 双路排名合并，`knowledge_id` 去重 | `agents/tools.py#rrf_merge` |
| `weighted_rerank` 加权重排 | 故障关键词命中优先 | `agents/tools.py#weighted_rerank` |
| 阈值过滤（0.15） | 丢弃低相关案例 | `api/search.py` |
| `require_hybrid` 强制混合检索 | 首轮确定性 vector+BM25 双路，避免 ReAct 早停 | `agents/retrieval_agent.py` |
| `_filter_rerank_cases` 严格过滤 | 设备精确匹配 + 故障关键词命中，剔除跨设备/泛相似案例（根治串味） | `api/search.py` |
| `fault_decomposer` 多故障拆解 | 规则预检 + LLM 拆解复合故障，各故障分组检索/回答 | `agents/fault_decomposer.py` |

### 1.3 已实现 / 待实现的兜底

**已实现**：`_filter_rerank_cases` 严格过滤为空时，回退宽松过滤的 top2（防止误伤导致"未检索到"）；专家模式全程 `asyncio.wait_for` 超时兜底（拆解 20s / 单故障 60s / 多故障 90s），超时返回降级提示而非卡死。

**待实现**：在 `/answer/stream` 中，若检索最高分 < 0.15（基本没查到），用 LLM 改写查询重试一次。只多 0~1 次 LLM 调用，成本低。

## 二、规模增长带来的预期问题

| 问题 | 现象 | 根因 |
|---|---|---|
| 阈值失真 | 固定 0.15 无法区分"没查到"和"查到但不相关" | 案例变多后分数分布变化 |
| 改写策略单一 | 一种改写法救不回"没查到"的多种原因 | 模糊、黑话、分类宽等不同失败原因 |
| 召回不足 | top-8 可能错过正确案例 | 相关案例变多，一步到位截断太早 |
| 检索变慢 | Milvus / PostgreSQL 查询耗时上升 | 数据量增大，索引未同步优化 |
| 区分度下降 | 相似案例过多，分数挤在一起 | 近似知识重复增长 |

---

## 三、调优方向一：轻量兜底方案演进

### 3.1 现状（拟定）

```python
# 检索后判断
if max_score < 0.15:
    → LLM 改写查询 → 重试一次
```

### 3.2 演进 A：阈值动态化

固定阈值 → 按当前知识库分数分布计算：

```python
# 按查询类型分阈值
if 精确查询（含故障码/编号）: threshold = 0.30
else（模糊语义查询）:        threshold = 动态百分位（如 P30）
```

### 3.3 演进 B：改写策略多样化

一次改写生成多条候选查询并行重试：

```
策略 1  同义词扩展     "电机不转" → "电机无法启动 / 不运转 / 卡死"
策略 2  设备类型收窄   "机器报警" → "注塑机 报警"
策略 3  拆分长句       "温度过高且声音大" → 拆成两条分别查
```

### 3.4 演进 C：止损判断

重试一次仍无结果时，明确回复"知识库暂未收录，建议补充知识"，避免无限改写浪费成本。

## 四、调优方向二：两阶段检索（核心）

规模变大后，核心矛盾从"查不到"变为"查不准"。方案：**先多召回、再精排**。

```
阶段一（粗排）：Milvus + BM25 各召回 top 50~100 → RRF 融合
阶段二（精排）：对粗排结果精细重排 → 取 top 5~8 喂 LLM
```

精排手段可选（按投入成本排序）：
1. 升级现有 `weighted_rerank`（规则调参，成本最低）
2. Cross-Encoder 重排（"问题×案例"联合编码打分，更准但慢，适合精排阶段）
3. LLM 挑选（让 LLM 从粗排结果中挑最相关的 5 条，即"决策一体化"的轻量版）

---

## 五、调优方向三：索引层面

| 存储 | 现状 | 规模变大后的调整 |
|---|---|---|
| PostgreSQL | 已有 pg_trgm GIN 索引迁移（`7a8b9c0d1e2f`） | 确认索引实际生效；按需分区（按设备类型/时间） |
| Milvus | HNSW 索引 | 调优 HNSW 参数（M、efConstruction、nlist）；用 `device_type`/`fault_code` 标量字段做分区过滤 |

---

## 六、调优方向四：分面预过滤

知识库变大后，检索前先**收窄范围再搜**：

- 请求已带 `device_type` / `fault_code` 可选字段（`AnswerRequest` / `SearchRequest`）
- 后端先按设备类型过滤子集 → 再向量检索
- 收益：搜得快 + 更准
- 现状：字段已定义但前端基本未用，属于"低成本高收益"项

---

## 七、调优方向五：缓存层

高频问题（重复故障现象）走 Redis 缓存：

```
question + device_type → 检索结果缓存
知识库版本号变更 → 缓存失效
```

- 减少重复查询的 Milvus / LLM 消耗
- 依赖现有 `cache_service.py`（Redis，端口 7379）

---

## 八、调优优先级建议

| 优先级 | 事项 | 收益 | 成本 |
|---|---|---|---|
| 1 | 两阶段检索（召回扩到 50，精排选 8） | 高（解决"查不准"） | 中 |
| 2 | 动态阈值 + 多策略改写（兜底升级） | 中（解决"查不到"） | 低 |
| 3 | 分面预过滤（device_type/fault_code） | 中（提速 + 提准） | 低 |
| 4 | 缓存层（Redis） | 中（省成本） | 低 |
| 5 | 索引调优（HNSW / pg_trgm / 分区） | 中（保持速度） | 低~中 |
| 6 | 完全体一体化（LLM 决策 + 混合检索 + LLM 回答） | 边际收益小 | 高（延迟/成本大） |

> 结论：**默认链路不建议做完全体一体化**。它让每次问答多 2~6 次 LLM 调用，延迟从几秒飙到 10~30 秒，而检索层已有的规则优化已覆盖大部分收益。
>
> 但该路径的可行性已被**专家模式（组合③）**验证：对复合/复杂问题做"选择性一体化"——用户主动切专家模式才触发，普通问答仍走快速链路。**原则：一体化只做用户主动触发的少数场景，不做默认全量**。

## 九、触发时机

| 观察信号 | 建议动作 |
|---|---|
| 用户反馈"问答查不到东西"，日志显示检索最高分普遍偏低 | 做优先级 2（动态阈值 + 多策略改写） |
| 用户反馈"答不到点子"，实际是召回不足（top-8 漏掉正确案例） | 做优先级 1（两阶段检索） |
| 检索接口 P95 延迟明显上升 | 做优先级 3/5（分面 + 索引） |
| DeepSeek/Milvus 调用成本升高 | 做优先级 4（缓存） |

> 核心原则：**用观察信号驱动，不提前过度设计**。当前阶段保持现状即可。
