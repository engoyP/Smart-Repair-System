# 钉钉问答联通复用追踪模式 · 策略与实现方案

> 钉钉机器人的故障问答从「对话式追踪」升级为「结构化追踪」：A/B/C 排查方向逐步引导、步骤计数、解决判定、维修总结；解析不了的操作反馈自动重发格式指引，不打断排查。**乙方智能诊断域核心逻辑零改动**，全部改动落在甲方钉钉接入层，复用乙方 `guided_repair_agent` 的公开方法。

**状态**：✅ 已落地（2026-08-17）　**渲染**：Phase 1 纯文本（互动卡片留作可选升级）

---

## 一、背景与目标

钉钉维修员向机器人发故障描述时，之前走的是**对话式追踪**（`guided_repair_agent.chat`），每轮只给「分析 + 唯一一个操作」，自由文本多轮对话。而系统已有的**结构化追踪**（`start_diagnosis` / `next_step`）具备更强的排查闭环能力，却只在 HTTP 端暴露（`/guided-repair/start` + `/step`），钉钉侧完全没复用。

目标：让钉钉问答**联通复用结构化追踪模式**——逐步给 A/B/C 排查方向、跟踪步骤、检测"已解决"并输出维修总结，让排查过程可追溯、可收口。

## 二、现状与差距

**改造前钉钉 repair 链路**：
```
robot_handler.handle_robot_message
  → robot_graph.invoke_robot → repair_node
    → mcp/tools.guided_repair_chat   （对话式，纯自由文本）
      → guided_repair_agent.chat_sync
```

**结构化追踪已有但钉钉没用上的能力**（`guided_repair_agent.py`）：
- `start_diagnosis` (L234)：检索知识库 → LLM 生成 step 1，输出 **2-3 个 A/B/C 选项**（`RepairOption.id / cause / diagnostic_action`）+ message
- `next_step` (L307)：以 **`selected_option / action_taken / device_status` 三字段**反馈续接 → 下一步选项
- 内置 **solved 判定**（"解决/正常/恢复/好了…" → 成功总结 `_generate_success_summary`）、**MAX_STEPS=30** → 最终总结、会话 `status: diagnosing / completed`

**差距三处**：① 钉钉没走结构化入口；② 自由文本 → 三字段（选项/动作/状态）的解析层缺失；③ 没有「新故障开新会话 vs 反馈继续排查」的状态判定。

## 三、方案设计

### 3.1 路由分层

```
钉钉消息 → robot_graph.repair_node
                 │
                 ▼
    mcp.tools.guided_repair_track(staff_id, text)     ← 新增路由层
                 │
     ┌─── 状态判定（guided_repair_agent.get_session_status）
     │       │
     │ 无会话 / completed / 会话过期 ──► start_diagnosis(text)  → 结构化 step1（A/B/C）
     │       │
     │ diagnosing（结构化会话）──► 消息归类：
     │         ├─ 含「新问题/重新开始…」──► start_diagnosis(新会话)
     │         ├─ 解析出操作反馈 ────────► next_step(session_id, 三字段)
     │         └─ 解析失败 ─────────────► 重发格式指引（不新开会话，零 LLM）
     ▼
   文本渲染 _render_guided_step_text → _send_reply 回钉钉
```

### 3.2 会话状态机（每 staff）

| staff 会话状态 | 触发 | 动作 |
|---|---|---|
| 无会话 / `completed` / 24h 过期 | 任意故障文本 | `start_diagnosis` 开新会话，映射新 session_id |
| `diagnosing` 且结构化 | 消息含「新问题 / 重新开始 / 换个故障…」 | 覆盖开新会话 |
| `diagnosing` 且结构化 | 正则/LLM 解析出三字段 | `next_step` 续接，更新最后活动时间 |
| `diagnosing` 且结构化 | 解析失败 | 重发格式指引，**不覆盖会话** |

> 判定只读：`get_session_status(session_id)` → `(status, is_structured)`。`is_structured` 判断会话是否由 `start_diagnosis` 创建（含 `history` 选项结构）；历史对话式会话（`chat` 创建、无 `history`）一律视为新会话重新开始，平滑迁移。

### 3.3 操作反馈解析（自由文本 → 三字段）

`next_step` 需要结构化三字段，钉钉用户只会发自然语言。解析器 `_parse_action_feedback`（mcp/tools.py）：

1. **正则快路**（零成本零延迟）：
   - 选项：`选(了)?[A-Ca-c0-9一二三①-⑨]`（"选A / 选了C / 选①"），或句首裸选项字母 `^B，…`
   - 映射：`①/1/一→A`、`②/2/二→B`、`③/3/三→C`；非标 id 用当前选项表兜底
   - 动作/状态切分：按状态连接词（结果/现在/然后/之后/试机…）切开；无连接词则按未解决词优先判定——**「还不行/不可以/没反应/依旧」→ 仍异常，「正常/好了/恢复」→ 恢复正常**（未解决词先于已解决词判断，避免"不行"误命中"行"）
2. **LLM 兜底**：正则取不到选项时，调 DeepSeek 抽三字段（低温度、15s 超时、失败降级）；只返回 `action_taken` 非空的结果
3. **仍失败** → 返回 `None`，上层重发格式指引，不新开会话

### 3.4 文本渲染（Phase 1）

`_render_guided_step_text` 把 `GuidedRepairStep` 渲染成钉钉 markdown，示例：

```
**第 2 步 · 排查方向**

当前排查方向如下：

【下一步选项】
**A** 保险丝烧断
　→ 用万用表测保险丝两端，正常应导通
**B** 电机过载
　→ 测电机电流，正常应<5A

请按格式回复：**选选项 + 执行的操作 + 执行后设备状态**
例如：选A 测量了电机电压 恢复正常
排查另一个故障，回复「新问题」
```

`completed` 步骤渲染「排查结束 · 第 N 步」+ 成功/最终总结。

## 四、交互流程示例

```
维修员：注塑机温度过高怎么办
机器人：**第 1 步 · 排查方向** …【选项 A/B/C】… 请回复：选A + 操作 + 状态

维修员：选B 检查了冷却水流量 还不行
机器人：**第 2 步 · 排查方向** …（基于 B 的执行结果给出下一步）…

维修员：选A 更换了热电偶 温度恢复正常
机器人：**排查结束 · 第 3 步** 问题已解决！故障原因：… 处理方法：…

维修员：新问题   ← 排查另一个故障
机器人：**第 1 步 · 排查方向** …（新会话）
```

## 五、实现落地

| 文件 | 改动 | 归属 |
|---|---|---|
| `backend/app/mcp/tools.py` | 新增 `guided_repair_track` + `_parse_action_feedback` / `_split_action_status` / `_map_option` / `_llm_parse_feedback` / `_render_guided_step_text` + 解析常量 | 甲方 |
| `backend/app/agents/robot_graph.py` | `repair_node` 改调 `guided_repair_track`（一行） | 甲方 |
| `backend/app/agents/guided_repair_agent.py` | 新增只读方法 `get_session_status` / `get_current_options`（**乙方唯一增量，不改任何逻辑**） | 乙方 |

复用的既有资产：`start_diagnosis` / `next_step` / `GuidedRepairStep` / `RepairOption`（HTTP 已用，契约稳定）、`cache_service` staff→session 映射（`mcp/staff_guid:*`，24h TTL）、`_send_reply` 文本回复通道。

> 原对话式入口 `guided_repair_chat`（`chat_sync`）**保留不动**，仍作为 MCP 工具暴露给外部 AI 客户端（`mcp/server.py`），钉钉 repair 意图切换到结构化追踪。

## 六、降级与边界

- **LLM 失败**：`start_diagnosis` / `next_step` 失败 → 透传 agent 自带失败 message，不崩
- **解析失败**：重发格式指引，**不覆盖进行中的会话**
- **会话过期**（24h TTL）→ 视为新故障重新 `start_diagnosis`
- **非结构化旧会话** → 视为新会话，平滑迁移
- **会话内闲聊**：无选项且非反馈 → 重发指引（不引对话式混会话，避免结构混用）

## 七、分工与接口契约

- **甲方（钉钉域）**：实现 `guided_repair_track` 路由层 + 反馈解析 + 文本渲染，只做消息接线，不改智能诊断逻辑
- **乙方（智能诊断域）**：只新增两个只读方法 `get_session_status` / `get_current_options`，供甲方判断会话续接方式

> 归属：本方案归「钉钉整体归甲方」范畴，乙方 Agent 逻辑零改动（仅加只读接口）。详见《两人任务分工方案》接口契约 ⑥。
